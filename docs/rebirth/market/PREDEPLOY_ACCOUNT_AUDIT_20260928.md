## 유료 비공개 테스트의 계정 게이트 — 제출 직전 순서

1. **판매자 지급 정보를 완성한다.** 9/29 개인 결제 프로필 연결은 Play 결제 대시보드로 검증됐다. 대시보드는 `수익을 지급받으려면 결제 수단을 추가하세요`라고 안내했다. 계정 소유자의 은행 지급 수단과 요구되는 세금 정보·확인 절차는 별도다. 수익화 계정의 **전체 법적 주소는 Play에 공개**될 수 있다. [Play 결제 프로필 생성](https://support.google.com/googleplay/android-developer/answer/7161426?hl=en), [계정/지급 수단 요구사항](https://support.google.com/googleplay/android-developer/answer/13628312?hl=en), [판매자 주소 공개](https://support.google.com/googleplay/android-developer/answer/13634081?hl=en).
2. **결제 라이브러리가 든 첫 Play 테스트 버전이 게시된 후 상품을 설정한다.** 9/29 판매자 연결 뒤 Console `일회성 제품` 페이지는 `앱에 아직 일회성 제품이 없습니다`와 `일회성 제품을 추가하려면 결제 권한을 APK에 추가해야 합니다`, `새 APK 업로드`를 표시했다. Alpha에는 **바이너리가 없는 임시 출시만** 있으므로 로컬 AAB만으로 상품 조회를 검증할 수 없다. Google의 공식 순서도 Billing Library 포함 앱 버전의 *테스트 트랙 게시*를 요구한다. `status_window_plus_01`을 **비소모성 Buy 일회 구매**로 만들고, 상품 이름·설명·세금/규정 선택과 Buy 구매 옵션 ID·한국/일본/대만/미국/캐나다/프랑스 가격·판매 가능 국가를 확인한다. **Draft 구매 옵션은 앱의 Billing Library 조회에 반환되지 않고 Active 옵션만 반환**된다. 실제 SKU ID·구매 옵션·현지 가격 조회를 Play 설치본에서 확인한다. `in_app_purchase_android 0.5.3`의 로컬 Gradle 의존성은 Billing Library 8.0.0이지만 실제 카탈로그 반환은 아직 미검증이다. [Billing 준비](https://developer.android.com/google/play/billing/getting-ready), [일회성 상품 구성](https://support.google.com/googleplay/android-developer/answer/16430488?hl=en).
3. **백엔드 비용과 보안 약관을 확정한다.** Functions와 현재 없는 Firebase Storage 기본 버킷은 이 프로젝트의 Spark에서 운영할 수 없으며 Blaze 결제 계정 연결이 필요하다. Functions 배포에는 Cloud Build/Artifact Registry, 코드의 `reconcilePlayVoidedPurchases`에는 Cloud Scheduler 작업, `acknowledgePlayPurchase`에는 Cloud Tasks 큐, RTDN에는 Pub/Sub가 따른다. 요금은 서비스별 사용량과 저장소 지역에 따라 달라진다. 예산 **알림은 차단 장치가 아니고**, Firebase의 서비스별 spend cap도 지원 서비스에 한정되고 지연 초과분이 청구될 수 있다. 따라서 원하는 월 위험 한도와 청구 계정을 확인하기 전에는 Blaze 전환·버킷/함수/큐 생성을 하지 않는다. [Functions와 Blaze](https://firebase.google.com/docs/functions/get-started), [Storage Blaze 요건](https://firebase.google.com/docs/storage/faq-and-troubleshooting), [Cloud Scheduler 비용](https://firebase.google.com/docs/functions/schedule-functions), [Cloud Tasks 비용·자동 큐](https://firebase.google.com/docs/functions/task-functions), [지출 제한의 범위](https://firebase.google.com/docs/projects/billing/spend-caps).
4. **Play Integrity·App Check를 순서대로 연결한다.** Play 앱 무결성에서 Cloud 프로젝트 `lifequest-crossing-2026`를 연결하고, 같은 Firebase 프로젝트의 App Check에서 Android 앱/배포 SHA-256을 Play Integrity 제공자로 등록한다. `Play Integrity API` 접근은 해당 약관 수락을 의미한다. 등록만으로 보안 **enforcement**가 켜지지 않으며, 먼저 실제 Play 설치본의 토큰과 정상 호출 지표를 확인해야 한다. 현재 SHA-256을 Firebase 앱에 등록한 것과 App Check 등록은 별개다. [Firebase 설정·단계적 enforcement](https://firebase.google.com/docs/app-check/android/play-integrity-provider), [Play Integrity 약관](https://developer.android.com/google/play/integrity/terms).
5. **Google Play Developer API와 알림을 연결한다.** Cloud 프로젝트에서 Google Play Developer API를 활성화하고 서버 실행 서비스 계정을 Play Console `Users and permissions`에 초대하여 결제 검증/ack에 필요한 `View financial data, orders, and cancellation survey responses`와 `Manage orders and subscriptions`, 누락 환불 조회에 필요한 `View financial reports` 권한을 실제로 확인한다. 서버는 Application Default Credentials를 쓰므로 개인키 JSON을 앱이나 저장소에 넣지 않는다. 예전 지침과 달리 **개발자 계정과 Cloud 프로젝트의 별도 링크는 API 접근의 필수 단계가 아니다**. RTDN Pub/Sub 토픽 `lifequest-play-billing-events`에 `google-play-developer-notifications@system.gserviceaccount.com`의 Publisher 권한을 주고 앱별 RTDN에서 **일회성 상품 포함** 옵션과 테스트 메시지 전달을 검증한다. RTDN 자체만으로 권한을 바꾸지 않고 Developer API를 재조회한다. [API 접근·권한](https://developers.google.com/android-publisher/getting_started), [Voided Purchases 권한](https://developers.google.com/android-publisher/voided-purchases), [RTDN 설정](https://developer.android.com/google/play/billing/getting-ready).
6. **실제 라이선스 거래로 닫는다.** Play 라이선스 테스터와 비공개 테스트 참여자 명단은 목적이 다르다. 일반 비공개 트랙 테스터의 인앱 구매는 실제 요금이 청구될 수 있으므로 외부 모집자에게 구매를 요구하지 않는다. 계정 소유자의 별도 라이선스 테스터가 구매·보류·취소·재설치 복원·환불·권한 회수와 서버 장애 재시도를 확인한다. 테스트 구매는 매출이나 시장 수요가 아니다. [Play 결제 테스트](https://developer.android.com/google/play/billing/test), [라이선스 테스트 설정](https://support.google.com/googleplay/android-developer/answer/6062777?hl=en).

## 다음 배포 요청 때의 확인 순서

1. **계정 상태를 먼저 읽는다.** Play Console에서 동일 개발자·앱·Alpha 초안/프로덕션 제한·앱 콘텐츠 오류·AAB 업로드 가능 여부를 재확인한다. Firebase Console에서 실제 요금제, Functions, Auth, App Check와 Cloud Tasks/Pub/Sub 상태를 확인한다. 9/21의 Chrome 파일 선택 제한과 Play Console 오류가 해결됐다고 추정하지 않는다.
2. **판매 운영을 구성한다.** 개인 결제 프로필 연결은 9/29 확인됐다. 지급 은행 계좌와 필요한 세금·인증 상태를 확인한다. [Play Billing 준비 문서](https://developer.android.com/google/play/billing/getting-ready)에 따라 Billing Library를 포함한 첫 테스트 버전 게시 후 최종 SKU·지역 가격을 설정한다. 9/29 Console도 바이너리 업로드 전에는 새 상품 버튼 대신 `새 APK 업로드`를 표시했다.
3. **로그인과 결제 백엔드를 실제 연결한다.** 업로드·Play 배포 인증서의 SHA-1/SHA-256 네 개와 [공식 Firebase Auth CLI 절차](https://firebase.google.com/docs/auth/configure-providers-cli)의 Google·이메일·익명 제공자 설정은 9/28 등록·배포했고, 갱신한 `google-services.json`의 Android OAuth 항목 두 개를 확인했다. 다음에는 실제 설치본에서 Google 로그인을 검증한다. [Firebase Functions 배포는 Blaze가 필요](https://firebase.google.com/docs/functions/get-started)하고 [Firestore TTL 삭제에도 비용이 발생할 수 있으므로](https://firebase.google.com/docs/firestore/pricing) 요금제·결제 계정·예산을 확정한 뒤 Storage 버킷, App Check, 운영 Firestore/Storage 규칙, TTL field override, Functions·비공개 작업 큐를 배포하고 오류/재시도 경로를 확인한다. [Play Developer API 안내](https://developers.google.com/android-publisher/getting_started)에 따라 서버 실행 계정의 API 및 Play 권한을 구성한다. 비밀 서비스 계정 키 다운로드 대신 관리형 실행 자격을 우선한다.
4. **환불 알림 경로를 검증한다.** [Play RTDN 설정](https://developer.android.com/google/play/billing/getting-ready)의 토픽, Play 송신자 Publisher 권한, 앱별 RTDN 연결과 **일회성 상품 포함** 알림 유형을 확인하고 테스트 메시지를 실제 함수가 받는지 확인한다. 알림만으로 권한을 바꾸지 말고 Play Developer API 재조회까지 검증한다.
5. **정확한 출시 후보로 라이선스 테스트한다.** 구매/보류/취소/재설치 복원/환불·권한 회수, 서버 장애·작업 큐 재시도, 계정 삭제를 Play 설치본에서 확인한다. 테스트 거래는 매출이나 유료 수요의 증거가 아니다.
6. **비공개 트랙을 실제 게시한 뒤 테스터를 모집한다.** [Google의 비공개 테스트 안내](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en)에 따르면 초안에는 참여 링크가 나타나지 않는다. 실제 opt-in 12명/14일 조건은 [개인 계정 요구사항](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)에 따라 집계한다. 계정의 프로덕션 접근 승인 전에는 정식 출시를 완료했다고 표시하지 않는다.

이번 점검에서 **업로드·Play 배포 인증서 등록, Auth 제공자 배포, 두 Android OAuth 설정 갱신**까지 진행했다. `firebase deploy --only auth --dry-run`은 예상과 달리 기본 Web App을 한 개 생성하는 부작용이 있었으며, 그 뒤 실제 Auth 배포가 성공했다. Spark·Storage 미사용·App Check 미등록·Play 판매자 계정 미설정·Alpha 바이너리 미업로드 상태를 직접 확인했다. TTL 정책은 원격에 없고 실거래도 없으므로 유료 판매 준비 완료 판정은 내릴 수 없다. 판매자/Blaze 설정과 실제 라이선스 거래 검증이 다음 증거다.
