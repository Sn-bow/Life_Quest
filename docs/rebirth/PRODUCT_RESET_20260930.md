# 제품 재검토: 매출을 위한 앱을 먼저 만든다 · 2026-09-30

## 사용자 결정과 현재 판정

사용자가 요구한 완료 기준은 **Play에 올릴 파일**이 아니라, 사람들이 반복해서 쓰고 돈을 낼 만한 콘텐츠·핵심 사용 경험·UI/UX·유료 가치가 모두 연결된 앱이다. 상태창과 일정관리는 출발 소재일 뿐 고정된 제품 정의가 아니다. 기존 Play/Firebase 설정과 서명 빌드는 이력으로 보존한다. 제품 판단과 구현보다 콘솔 등록·상품 생성·배포를 앞세우지 않는다. 별도 명시적 배포 요청 전 AAB 업로드나 테스트 트랙 게시는 여전히 금지한다.

**현 상태는 제품 완성이 아니다.** 첫 사용자는 0 XP/0 능력치 상태창을 보고, 가치 있는 첫 행동은 다른 탭에 있다. 사용자가 적는 자유 목표는 모델이 없는 기본 추천 엔진에서 쓰이지 않는다. 고성능 기기에서 선택 다운로드하는 2.59 GB 모델은 대다수 사용자의 첫 가치 제안이 될 수 없다. 현재 Plus의 외관·30/90일 집계·내보내기는 첫날 시연할 가치가 작고 무료 보고서와 겹친다. 이는 코드/화면 감사의 결론이며 사용자의 실제 반응 측정 결과가 아니다.

## 시장에서 확인한 것과 확인하지 못한 것

[LifeUp](https://play.google.com/store/apps/details?id=net.sarasarasa.lifeup)은 일회 구매형 생활 게임화 앱으로 10만+ 다운로드를 표시한다. [Habitica](https://play.google.com/store/apps/details?id=com.habitrpg.android.habitica)는 500만+, [Finch](https://play.google.com/store/apps/details?id=com.finch.finch)는 1,000만+ 다운로드를 표시한다. 상태창·AI 퀘스트를 표방하는 [LevelsUp](https://play.google.com/store/apps/details?id=com.levelsup.rpg.habittracker) 같은 신작도 있다. **범주 수요와 경쟁은 존재하지만 Life Quest의 결제 수요·전환율·수익성을 입증하지 않는다.** XP, 능력치, AI라는 단어만으로 차별화된다고 가정하지 않는다.

## 새 제품 가설

핵심 문제는 막연한 목표 앞에서 **지금 실행할 첫 행동을 정하기 어렵다**는 것이다. 앱은 목표·가능 시간·에너지·최근 완료/거절/어려움 기록을 바탕으로 안전하고 구체적인 3~10분 행동 **하나**를 빠르게 제안하고, 사용자가 수락·거절·조정하도록 돕는다. 완료 후에는 실제 XP/기록/목표 진행을 즉시 확인하게 하고 다음 날 제안이 바뀌어야 한다. 상태창은 이 과정을 즐겁게 보여주는 표현 방식이지 빈 숫자를 바라보게 하는 홈이 아니다. 이 가설이 약하면 상태창이라는 껍데기를 위해 제품을 유지하지 않는다.

수익 가설은 기존 `status_window_plus_01`의 외관·집계·파일 묶음보다 **적응형 성장 경로**에 있다. 무료 사용자는 한 목표의 실제 첫 행동과 일상 퀘스트·기본 기록을 온전히 사용한다. 유료 후보는 사용자 목표를 여러 날의 검토 가능한 단계로 나누고, 완료/거절/중단 후 다음 단계를 다시 계획하며, 본인의 행동과 목표 진척을 연결해 보여주는 완성된 다주 경로다. 외관·내보내기는 부가 가치일 수 있지만 구매의 주된 이유로 가정하지 않는다. 구독보다 명확한 범위의 일회 구매를 우선 시험한다. **가격·상품 구성·SKU는 아직 결정하지 않는다.** 이 경로가 쓸모없는 반복 템플릿에 그친다면 유료 상품으로 내지 않는다.

## 구현과 품질 게이트

1. 첫 30~60초 안에 이름/실제 목표/가능 시간을 간단히 입력하고, 본인에게 맞는 첫 퀘스트를 상태창에서 수락할 수 있게 한다. 모델이 없는 기기에서도 목표 분야를 반영해야 한다.
2. 수락→완료→실제 상태 변화→다음 행동의 동선을 한 번에 이해할 수 있어야 한다. 거절·어려움·쉬는 날에는 벌점 대신 다음 제안을 조정한다. 돌발 퀘스트는 실제 제안이 있을 때만 눈에 띄게 보이고, 거절은 손해가 없음을 명확히 한다.
3. 최소 7일 사용을 가정한 여러 날의 진전·회복 시나리오를 네 언어의 실제 콘텐츠로 완성한다. 동일 문구를 무작위로 바꾸는 것을 개인화/AI라고 부르지 않는다. 모델 다운로드·호환성·출력 실패 시에도 기본 경로가 작동해야 한다.
4. 유료 혜택은 본인의 실제 데이터 또는 정직한 예시로 구매 전에 시연하고, 무료 기능과의 차이를 즉시 알 수 있어야 한다. 유료 경로의 구매·복원·환불은 기술적으로 검증되기 전 완료로 보지 않는다.
5. 첫 사용/다음날/7일째/오프라인/기기 변경/큰 글자/작은 휴대폰/태블릿/네 언어를 실제 화면과 행동으로 확인한다. 이미지·아트는 사용자 지시에 따라 생성 이미지 또는 사용 허가된 자산을 쓰며 수제 SVG/HTML 그림을 쓰지 않는다.
6. 동의 기반 최소 계측으로 첫 제안→수락→완료, 다음날·7일 복귀, 유료 혜택 미리보기→가격 노출→실구매·환불을 구분한다. 매출, 순이익, 전환율을 실제 데이터 없이 주장하지 않는다. Play 라이선스 테스트 결제는 시장 매출로 세지 않는다.

## 작업 순서

첫 행동과 목표 관련성을 구현·QA → 7일 경로의 내용과 적응 품질 구현·QA → 유료 가치가 실제로 무료 경험보다 충분한지 검토 → 그 결론에 맞는 상품·가격·결제 UX 재설계 → 실제 Play 구매/환불 검증을 포함한 비공개 테스트 준비 → 사용자 배포 지시와 플랫폼 요건에 따라 출시. 기존 콘솔 설정은 마지막 단계의 준비 자료다. 시장 구매 의사는 실제 사용자/거래 없이는 확정할 수 없으며, 근거가 약하면 출시를 밀어붙이지 않고 제품 방향을 다시 바꾼다.
